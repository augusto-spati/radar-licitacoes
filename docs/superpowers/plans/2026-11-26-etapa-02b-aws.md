# Radar de licitações: plano 2b (radar na AWS)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pôr o radar no ar na AWS, com infraestrutura como código: front no S3 + CloudFront, API em Lambda atrás do API Gateway, login por código no e-mail, coleta diária em Fargate agendada pelo EventBridge, banco no Neon, alerta de orçamento e deploy pelo GitHub Actions com OIDC.

**Architecture:** spec `2026-11-26-etapa-02-design.md`, seção "Arquitetura" e "Respostas à revisão".
- O CloudFront serve o front e encaminha `/api/*` ao API Gateway. Front e API ficam na mesma origem, então não precisa de CORS.
- A Lambda fica fora de VPC e acessa o Neon por TLS.
- O coletor roda num container Fargate numa sub-rede pública, com IP público e sem NAT.

**Escopo deste plano:** só infraestrutura e empacotamento. A ida das páginas brutas para o S3 é outra etapa (**2b-brutos**). Ela mexe em `coleta`, que a etapa 3 está alterando agora, e só começa depois do merge da etapa 3.

**Tech Stack:** Terraform ≥ 1.10 (provider `hashicorp/aws` ~> 5.x, travado no `.terraform.lock.hcl`), Docker, Mangum, Amazon Cognito, GitHub Actions OIDC.

**Spec:** `docs/superpowers/specs/2026-11-26-etapa-02-design.md`

## Global Constraints

- **Região:** `us-east-2`. Todos os recursos levam as tags `projeto=radar-licitacoes` e `ambiente=prod`.
- **Repositório público:** nenhum segredo no repositório.
  - A URL do Neon fica no SSM Parameter Store, como `SecureString` em `/radar/prod/database_url`.
  - O e-mail do Budgets e os e-mails com acesso entram por variável do Terraform num `terraform.tfvars` que **não** é versionado. Versiona-se só um `terraform.tfvars.example`.
- **Custo zero ou perto disso:**
  - proibido NAT Gateway, load balancer, instância RDS e qualquer recurso que cobre por hora parado;
  - o Budget mensal é de **US$ 5**, com alertas em 50%, 80% e 100% (real) e 100% (previsto).
- **Estado do Terraform:** fica num bucket S3 com versionamento e lock nativo (`use_lockfile = true`). O bucket é criado por um diretório `infra/bootstrap/`, aplicado uma vez, com estado local que não vai para o repositório.
- **Validação sem conta AWS:** em CI e localmente, `terraform fmt -check -recursive`, `terraform init -backend=false` e `terraform validate` em cada diretório. O CI ganha o job `infra`, que **não** acessa a AWS.
- **Variáveis de ambiente da aplicação:**
  - Lambda e Fargate recebem `RADAR_DB_NULLPOOL=true` e `RADAR_CONFIG_FILTRO=/var/task/config/filtro.toml` na Lambda (no Fargate, o caminho equivalente na imagem);
  - a URL do banco vem do SSM na inicialização. A política IAM dá acesso só a esse parâmetro.
- **Coleta agendada:** todo dia às 06:00 de Brasília (`cron(0 6 * * ? *)`, fuso `America/Sao_Paulo`, no EventBridge Scheduler), rodando `radar atualizar`. A task tem 0,25 vCPU, 0,5 GB e timeout de 2 h.
- **Login:**
  - código de uso único por e-mail, sem senha, só para os e-mails da variável `emails_com_acesso`;
  - cadastro aberto desligado;
  - a API exige JWT válido em `/api/*`, exceto `/api/status`.
- **Commits:**
  - terminam com:
    ```
    Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
    Claude-Session: https://claude.ai/code/session_012v6r8uz1aiPHNQoDZ66AVf
    ```
  - os que mexem em arquivos guardados do front ou do CI levam também `Contrato-Front: aprovado`.
- **Branch e merge:** o trabalho é no branch `etapa-02b-aws`, criado a partir da `main`. O merge acontece por PR.

## Review Focus

1. **Um `terraform apply` não pode criar nada que cobre parado.** Um teste estático lista os tipos de recurso da configuração e reprova se aparecer `aws_nat_gateway`, `aws_lb`, `aws_db_instance`, `aws_rds_cluster` ou `aws_instance`.
2. **Nenhum segredo no estado versionado nem no repositório.** O `.gitignore` cobre `*.tfstate*`, `terraform.tfvars` e `.terraform/`. O teste da Task 2 confere.
3. **Lambda com cold start ruim.** O app FastAPI é criado uma vez por container, o handler reaproveita esse app, e o banco usa NullPool. Teste na Task 1.
4. **`/api/*` passando pelo CloudFront com id que contém `/`** (`pncp~.../2026` ou `sanepar~OE-345/26`). A barra precisa chegar ao API Gateway sem ser reescrita. Teste do handler com o evento real na Task 1, mais conferência na Task 8.
5. **Coleta agendada que falha não pode passar em silêncio.** O código de saída 1 vira falha da task no ECS. Um alarme do CloudWatch avisa por e-mail via SNS, com assinatura no e-mail do Budget, quando a task falhar ou não rodar em 26 h.

### Task 3: Front no S3 + CloudFront

**Files:** `infra/prod/front.tf`, com saídas em `outputs.tf`.

**Interfaces:**
- Bucket privado `radar-licitacoes-front-<account_id>`, acessado pelo CloudFront via **OAC** (origin access control). A política do bucket só permite o ARN da distribuição.
- **Distribuição:**
  - `default_root_object = "index.html"`;
  - comportamento padrão vai para o S3, com `CachingOptimized`;

  - certificado padrão do CloudFront, sem domínio próprio por enquanto;
  - `price_class = "PriceClass_100"`.
- **Saídas:** `url_site` e `id_distribuicao`.

### Task 4: API — ECR, Lambda, API Gateway, SSM, IAM

**Files:** `infra/prod/api.tf`, `infra/prod/ecr.tf`, `infra/prod/ssm.tf`.

**Interfaces:**
- **ECR:** repositórios `radar-api` e `radar-coletor`, com política de ciclo de vida mantendo as 5 imagens mais recentes e scan on push.
- **Lambda `radar-api`:**
  - `package_type = "Image"`, 512 MB, timeout 15 s, arquitetura `x86_64`;
  - variáveis do Global Constraint;
  - role com `AWSLambdaBasicExecutionRole` e `ssm:GetParameter` + `kms:Decrypt` só no parâmetro do banco.
- **API Gateway HTTP API:**
  - integração proxy com a Lambda, rota `ANY /api/{proxy+}`;
  - rota `GET /api/status` sem autorizador;
  - as demais com autorizador JWT do Cognito (Task 5). Até a Task 5 existir, a variável `exigir_login` (padrão `true`) controla o autorizador.
- **SSM:** cria o parâmetro `/radar/prod/database_url` como `SecureString` com valor `"preencher"` e `lifecycle { ignore_changes = [value] }`. O valor real é posto à mão pelo Augusto.
- **Imagem inicial:** a Lambda precisa de uma imagem existente. A variável `imagem_api` tem como padrão `<ecr>:bootstrap`, e o `infra/README.md` documenta o primeiro push antes do apply.

### Task 5: Login (Cognito, código por e-mail)

**Files:** `infra/prod/auth.tf`, front (`src/paginas/Entrar.tsx`, `src/dados/` com a sessão, `fonteApi` mandando o token), testes. Os arquivos guardados levam o trailer.

**Pesquisa antes de implementar (no relatório, com fontes):**
- qual plano do Cognito (Lite ou Essentials) oferece **login sem senha por código no e-mail (passwordless email OTP)**;
- o custo para 2 a 5 usuários por mês;
- se o envio de e-mail pelo Cognito sem SES basta (limite diário).

Se o passwordless exigir um plano pago acima do orçamento, a alternativa é a **Hosted UI com senha**, ainda com cadastro fechado. Nesse caso o implementador **para e reporta** antes de seguir.

**Interfaces:**
- **User pool:** `allow_admin_create_user_only = true`. Os usuários são criados pelo Terraform a partir de `emails_com_acesso`.
- **App client público:** sem segredo, fluxo `USER_AUTH` com `EMAIL_OTP`, ou o fluxo hosted com PKCE, conforme a pesquisa.
- **Autorizador JWT:** emissor = o user pool, audiência = o client.
- **Front:**
  - a tela `Entrar` usa o fluxo real: e-mail, código, tokens;
  - os tokens ficam em `sessionStorage`;
  - `fonteApi` manda `Authorization: Bearer <id_token>`;
  - um 401 manda para `/entrar`;
  - a lista de rotas **não muda**.

- [ ] **Step 2:** Testes do front, com o Cognito simulado:

### Task 6: Coleta agendada (Fargate + EventBridge Scheduler + alarmes)

**Files:** `infra/prod/coletor.tf`.

**Interfaces:**
- **Rede:** usa a VPC padrão e as sub-redes públicas por `data`, com `assign_public_ip = true`. O security group só tem saída.
- **Cluster:**
  - ECS `radar`;
  - task definition `radar-coletor` (Fargate, com a CPU, a memória e o comando do Global Constraint, logs no CloudWatch com retenção de 30 dias);
  - variáveis de ambiente iguais às da Lambda.
- **IAM:**
  - a execution role puxa do ECR e escreve logs;
  - a task role lê o parâmetro do SSM.
- **Scheduler:** `aws_scheduler_schedule` com o cron e o fuso do Global Constraint, alvo ECS RunTask, e role para `ecs:RunTask` + `iam:PassRole`.
- **Alarmes** (Review Focus 5):
  - uma regra do EventBridge pega `ECS Task State Change` com `stoppedReason`/`exitCode != 0` e publica no SNS `radar-alertas`;
  - um alarme do CloudWatch dispara quando não há log do coletor em 26 h.

### Task 7: Deploy pelo GitHub Actions com OIDC

**Files:** `infra/prod/github_oidc.tf`, `.github/workflows/deploy.yml` (novo, adicionado aos GUARDADOS e ao CODEOWNERS no mesmo commit, com o trailer).

**Interfaces:**
- **Provedor OIDC:** `token.actions.githubusercontent.com`. A role `radar-deploy` tem trust restrito a `repo:augusto-spati/radar-licitacoes:ref:refs/heads/main` e permissões mínimas:
  - push nos dois repositórios do ECR;
  - `lambda:UpdateFunctionCode` na `radar-api`;
  - `ecs:RegisterTaskDefinition` + `iam:PassRole` das roles do coletor;
  - `s3:PutObject/DeleteObject/ListBucket` no bucket do front;
  - `cloudfront:CreateInvalidation` na distribuição.
- **`deploy.yml`:**
  - roda em push na `main` e em `workflow_dispatch`, com `permissions: id-token: write, contents: read`;
  - passos: build e push das duas imagens (tag = SHA), atualização da Lambda e de uma nova revisão da task definition, build do front com `VITE_FONTE=api`, sync com `--delete` e invalidação de `/*`;
  - se o secret ou a variável `AWS_ROLE_ARN` não existir, o workflow sai com sucesso e um aviso. Até a conta existir, o deploy não quebra a `main`.
